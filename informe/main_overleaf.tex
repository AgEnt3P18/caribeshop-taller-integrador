\section{Introducción y alcance}
% =================================================================
CaribeShop, tienda en línea con sede en Cartagena, sufrió el año pasado dos caídas
(saturación durante una promoción y falla de su única máquina virtual) y una auditoría
encontró la contraseña de la base de datos en el repositorio y el puerto SSH abierto a
Internet. Este informe documenta el diseño, el despliegue \emph{como código} y la
validación empírica de una plataforma en Microsoft Azure que corrige esos tres problemas:
es \textbf{segura}, \textbf{escala automáticamente} y \textbf{sigue funcionando} cuando falla
un componente.

\begin{itemize}
  \item \textbf{Repositorio:} \url{https://github.com/AgEnt3P18/caribeshop-taller-integrador}
  \item \textbf{Herramientas:} Terraform 1.17 (azurerm 4.x), Azure CLI 2.93, GitHub Actions,
        Checkov 3.4, Locust 2.x, Python 3 (solo biblioteca estándar en la app).
  \item \textbf{Región:} \texttt{eastus} (zonas 1, 2 y 3). Tamaño \texttt{Standard\_D2s\_v4}
        (2 vCPU); la cuota regional de la suscripción es de 10 vCPU.
\end{itemize}

\section{Implementación paso a paso}
% =================================================================
\begin{enumerate}
  \item \textbf{Autenticación.} \texttt{az login} interactivo sobre el inquilino de la suscripción. El
        flujo \emph{device code} fue bloqueado por los \emph{security defaults} de Entra ID
        (\texttt{AADSTS530035}); se usó el flujo de código de autorización (PKCE).
  \item \textbf{Selección de región/tamaño} con \texttt{az vm list-usage} y \texttt{az vm list-skus}
        (cuotas por familia y restricciones por zona).
  \item \textbf{Bootstrap del backend} (\texttt{bootstrap/main.tf}): RG, cuenta
        \texttt{stcstfstate*} sin llaves, versionado, \emph{soft delete}, firewall y rol
        \emph{Storage Blob Data Contributor} para el operador.
  \item \textbf{Plataforma} (\texttt{infra/}): \texttt{terraform init -backend-config=backend.hcl},
        \texttt{plan -out} y \texttt{apply}: \textbf{33 recursos} creados en un solo \emph{apply}.
  \item \textbf{Configuración automática} (D3): \texttt{cloud-init.yaml.tftpl} escribe la app,
        su configuración no sensible y un servicio \texttt{systemd}. Un cambio de la app se
        desplegó con \texttt{terraform apply} + \texttt{az vmss reimage}, sin pasos manuales.
  \item \textbf{Validación} de configuración (\texttt{scripts/collect\_evidence.sh}), pruebas
        P1--P3 y recolección de evidencias en \texttt{evidencias/}.
\end{enumerate}

\begin{lstlisting}[caption={Fragmentos clave: autoscale con histéresis (E3) y rol de mínimo privilegio (S4).}]
rule { # scale-out
  metric_trigger { metric_name = "Percentage CPU", time_window = "PT5M",
                   operator = "GreaterThan", threshold = 70 }
  scale_action   { direction = "Increase", value = "1", cooldown = "PT5M" } }
rule { # scale-in: umbral distinto (histeresis), ventana y cooldown mas largos
  metric_trigger { metric_name = "Percentage CPU", time_window = "PT10M",
                   operator = "LessThan", threshold = 30 }
  scale_action   { direction = "Decrease", value = "1", cooldown = "PT10M" } }

resource "azurerm_role_assignment" "vmss_secret_reader" {
  scope                = azurerm_key_vault_secret.db.resource_versionless_id
  role_definition_name = "Key Vault Secrets User"
  principal_id = azurerm_linux_virtual_machine_scale_set.app.identity[0].principal_id }
\end{lstlisting}

\textbf{Justificación de la histéresis y los cooldowns.} Entre 30\,\% y 70\,\% no hay acción, lo
que evita oscilaciones (\emph{flapping}). El scale-out reacciona en 5 min y su cooldown
(5 min) cubre el arranque de una instancia ($\approx$\,40\,s de aprovisionamiento + $\approx$\,30--60\,s de cloud-init) más la estabilización de la métrica.
El scale-in es deliberadamente más lento (ventana y cooldown de 10 min): retirar capacidad
por error es más costoso (latencia, errores) que mantenerla unos minutos más.

\section{Resultados de las pruebas}
% =================================================================
Locust se ejecutó desde la red del equipo (Cartagena, RTT $\approx$ 200\,ms hacia \texttt{eastus}).
El \emph{endpoint} \texttt{/work} consume 40\,ms de CPU por petición (8 de cada 9 peticiones) y
\texttt{/} sirve la portada. Los CSV e informes HTML están en \texttt{evidencias/}.

\subsection{P1.1 Capacidad de una instancia}
Con el autoscale fijado en \texttt{min = max = 1} (\texttt{terraform apply -var min\_instances=1
-var max\_instances=1}) se aumentaron los usuarios de 5 en 5 (y luego de 10 en 10) cada 45\,s hasta 240.

\begin{figure}[H]
\centering
\includegraphics[width=0.86\textwidth]{figuras/p1_capacidad.png}
\caption{Latencia (mediana por escalón de las ventanas de Locust) frente a RPS con una sola instancia.}
\label{fig:cap}
\end{figure}

\begin{itemize}
  \item El \textbf{throughput se satura en $\approx$ 120 RPS} (la CPU llega al 98\,\%): desde 170
        usuarios agregar usuarios solo aumenta la cola y la latencia.
  \item \textbf{Capacidad sostenible: 119 RPS con p95 < 1 s} (190 usuarios, p95 = 960\,ms) y
        \textbf{112 RPS con p95 < 500 ms} (150 usuarios). El p95 pasa 1 s de forma sostenida desde
        200 usuarios.
  \item Al 70\,\% de CPU (umbral del autoscale) una instancia atiende $\approx$ 60--65 RPS.
  \item Los escalones con p95 exactamente 1,2\,s y p50 estable (círculos grises) \textbf{no son
        saturación}: corresponden al primer RTO de TCP (1\,s) más el RTT (0,2\,s), es decir, SYN
        perdidos en la red doméstica del cliente. Todos los fallos registrados son
        \texttt{ConnectTimeoutError} (fase de conexión), ninguno 5xx.
\end{itemize}

$\rightarrow$ 120 $\rightarrow$ 20 (12 min). Autoscale restaurado a 2--4 instancias.
Total: \textbf{207\,435 peticiones, 1\,143 fallidas (0,55\,\%)}.

\textbf{Análisis.} El autoscale se comportó según el diseño: ningún \emph{flapping}, scale-out

Fig.~\ref{fig:stair}: entre 00:16 y 00:20 la CPU estuvo entre 30 y 70\,\% y no hubo acciones.

el p50 subió a 330\,ms durante $\sim$\,5 min hasta que entró la 3.ª instancia (p50 230\,ms). La
4.ª instancia quedó lista a las 00:15:34, \textbf{6 segundos después de que la carga empezara a
bajar}: para picos cortos el autoscale reactivo llega tarde, lo que motiva la respuesta a la
pregunta 2.

la ventana es igual al de la línea base (los errores observados son de la red doméstica del
cliente, presentes antes y después de T0). La falla \emph{abrupta} sí produce errores: durante
$\sim$10--15\,s el balanceador sigue enviando conexiones nuevas a una VM que ya no existe, hasta
completar 2 sondeos fallidos. Con 2 instancias, la mitad del tráfico de esa ventana falla
(29\,\%); con 3 o 4 instancias la fracción afectada sería 1/3 o 1/4. Reducir el intervalo de
la sonda acorta esa ventana, a cambio de más tráfico de sondeo y mayor sensibilidad a falsos
positivos. La reparación automática tardó 11,3\,min (10\,min de gracia más la detección),
mientras que el autoscale repuso la capacidad mínima en menos de 2\,min.

\section{Preguntas de análisis}
% =================================================================
\paragraph{1. Instancias para 300 RPS con p95 < 500 ms.}
Con la capacidad medida (P1.1), una instancia sostiene $\approx$\,\textbf{112 RPS con p95 < 500 ms}
y $\approx$\,119 RPS con p95 < 1 s, con la CPU cerca del 98\,\%. Operar a ese nivel no deja margen,
así que se dimensiona al \textbf{70\,\% de CPU} (el umbral del autoscale), $\approx$\,62 RPS por
instancia: $\lceil 300/62\rceil = 5$ instancias, que consumen exactamente los 10 vCPU de la cuota regional. Para tolerar la pérdida de una
zona sin violar el objetivo se necesitan 2 instancias por zona (6 en total): al caer una zona
quedan 4 ($\approx$\,450 RPS). \textbf{Con la cuota actual solo es viable sin margen}: 10 vCPU por región
equivalen a 5 instancias \texttt{D2s\_v4}. Cambios: (a) solicitar aumento de cuota de la familia
DSv4 a $\geq$\,16 vCPU; (b) subir \texttt{max\_instances} a 6--8; (c) reducir el costo por petición
(caché de páginas, CDN para contenido estático, un servidor WSGI compilado en lugar de
\texttt{http.server}).

\paragraph{2. Tiempo de reacción del autoscale y pico a las 8:00 p.\,m.}
Medido en P1.2: desde que la CPU superó el 70\,\% hasta que la nueva instancia recibió
tráfico pasaron \textbf{5\,min 19\,s hasta la acción y $\approx$\,6\,min hasta que la instancia atendió tráfico}, compuestos por la ventana de evaluación (5 min de promedio), la
latencia de la métrica ($\sim$\,1--3 min), el aprovisionamiento ($\sim$\,1 min) y cloud-init
($\sim$\,1 min). Ante un pico súbito ese retraso se traduce en latencia alta y errores. Ajustes:
\begin{itemize}
  \item \textbf{Perfil programado} (\emph{recurrence}) de 19:30 a 22:30 (hora de Colombia) con
        \texttt{minimum = 4}: la capacidad ya está lista cuando empieza la campaña.
  \item \textbf{Autoscale predictivo} (VMSS, métrica de CPU): pronostica a partir de 7 días de
        historia y escala por adelantado; primero en modo \emph{forecast only} para validarlo.
  \item Reglas reactivas más agresivas solo en ese perfil: ventana \texttt{PT2M}, umbral 60\,\%,
        \texttt{ChangeCount = 2}.
\end{itemize}

\paragraph{3. Punto único de falla.}
Dentro de la región no hay un SPOF de infraestructura: IP pública, LB y VMSS son
zonal-redundantes. El \textbf{punto único de falla es la región \texttt{eastus}} (todo el
stack vive en ella) y, a nivel lógico, el \textbf{Key Vault} (una sola instancia regional; la
caché de 60\,s solo amortigua fallas cortas). También lo es la cuota: si una zona cae, el
reemplazo de capacidad depende de que haya vCPU disponibles. Eliminar el SPOF regional
requiere un despliegue activo-pasivo en una segunda región (p.\,ej. \texttt{centralus}) con
Azure Front Door: $\approx$\,USD 35/mes de Front Door Standard + tráfico, más el stack secundario
(mínimo $\approx$\,USD 174/mes con 2 instancias, o $\approx$\,USD 100 en frío con 1 instancia).
Es decir, $+$\,USD 135--210/mes, del 75\,\% al 120\,\% del costo base.

\paragraph{4. Si un atacante obtiene ejecución de código en una instancia.}
\begin{itemize}
  \item \textbf{Podría:} leer \texttt{db-password} usando la identidad administrada; alterar las
        respuestas de esa instancia; consumir CPU; consultar IMDS.
  \item \textbf{No podría:}
  \begin{itemize}
    \item leer otros secretos, llaves o certificados: el rol tiene alcance a un solo secreto;
    \item modificar la infraestructura: la identidad no tiene roles en ARM;
    \item entrar o moverse por SSH/RDP: no hay IP pública y el NSG niega toda entrada salvo el puerto 80;
    \item exfiltrar a un servidor propio en Internet: el NSG niega el egress (prueba P3.2);
    \item leer o escribir en el Storage: no tiene rol de datos y las llaves compartidas están deshabilitadas;
    \item crear una NIC con IP pública: no tiene permisos y además la política lo niega.
  \end{itemize}
  \item \textbf{Riesgo residual:} la etiqueta \texttt{Storage.eastus} permite salir hacia
        \emph{cualquier} cuenta de almacenamiento de la región, incluso una del atacante, lo que
        abre un canal de exfiltración. Mitigación: \emph{service endpoint policies}, \emph{private
        endpoints} o Azure Firewall con filtrado FQDN.
  \item \textbf{Detección:} las lecturas del secreto quedan registradas en
        \texttt{AzureDiagnostics} (S6). Tras un incidente se rota el secreto con
        \texttt{terraform apply -replace=random\_password.db}.
\end{itemize}

\paragraph{5. ¿Por qué el escaneo en el pipeline no sustituye a Azure Policy, ni viceversa?}
Checkov es \emph{preventivo y temprano}: revisa el código en cada PR, da retroalimentación antes
del despliegue y cubre buenas prácticas que no son de Azure (p.\,ej. \texttt{fmt}). Pero solo ve
lo que pasa por el repositorio: un cambio hecho desde el portal, la CLI o en otro repositorio
no lo atraviesa, y un \texttt{\#checkov:skip} puede silenciarlo. Azure Policy actúa en el plano
de control de ARM y aplica \emph{a cualquier cliente} (portal, CLI, Terraform o un atacante con
credenciales), además de auditar el inventario existente. Su limitación es que da la
retroalimentación tarde (al hacer \emph{apply}) y no conoce el contexto del código. Ambas capas
se complementan; P3.3 muestra que Policy bloquea incluso una petición que no viene de
Terraform.

\paragraph{6. El estado de Terraform contiene secretos.}
El estado guarda en texto claro el valor de \texttt{random\_password.db} (el secreto), la llave
privada SSH de \texttt{tls\_private\_key} y la topología. Protección aplicada:
\begin{itemize}
  \item backend remoto, nunca local ni en Git (\texttt{.gitignore});
  \item cuenta sin llaves compartidas: acceso solo con Entra ID y RBAC (\emph{Storage Blob Data
        Contributor} únicamente para el operador);
  \item firewall limitado a las IPs del operador, TLS 1.2 y cifrado en reposo;
  \item versionado y \emph{soft delete} de 7 días;
  \item bloqueo de estado mediante \emph{lease} de blob.
\end{itemize}
Si se filtrara: el atacante tendría la contraseña de la base de datos y la llave SSH (inútil
sin acceso de red al puerto 22) y conocería la topología. Respuesta: rotar el secreto
(\texttt{-replace}), regenerar la llave, revisar los logs de acceso a la cuenta y al Key Vault.
Mejora recomendada: usar atributos \emph{write-only} (\texttt{value\_wo} en
\texttt{azurerm\_key\_vault\_secret}, Terraform $\geq$ 1.11) y \emph{ephemeral resources} para que el
secreto no llegue al estado.

\section{Conclusiones}
% =================================================================
\begin{enumerate}
  \item \textbf{Los tres incidentes de CaribeShop quedan cubiertos con evidencia medida.}
        \begin{itemize}
          \item \textbf{Saturación:} el autoscale pasó de 2 a 4 instancias y volvió a 2, con 0,55\,\% de error
                en 207\,435 peticiones.
          \item \textbf{Falla de una máquina:} la falla lógica se absorbió en 8\,s sin errores adicionales;
                la abrupta produjo 15\,s de errores y la capacidad mínima volvió en 109\,s.
          \item \textbf{Hallazgos de auditoría:} no hay secretos en el código, no hay puertos de
                administración expuestos y un PR que abría SSH fue bloqueado por el pipeline.
        \end{itemize}
  \item \textbf{La seguridad se construyó en capas independientes} y cada una se demostró por
        separado:
        \begin{itemize}
          \item NSG con egress denegado;
          \item firewall del Key Vault, que rechazó incluso a un usuario con el rol correcto;
          \item RBAC con alcance a un único secreto;
          \item Azure Policy, que rechazó recursos creados fuera de Terraform;
          \item auditoría KQL.
        \end{itemize}
  \item \textbf{Medir antes de configurar.} La capacidad medida (119 RPS por instancia, 112 RPS
        con p95 < 500\,ms) y la relación CPU--RPS permitieron justificar los umbrales del
        autoscale y dimensionar el escenario de 300 RPS (5 instancias, justo en el límite de la
        cuota).
  \item \textbf{El autoscale reactivo tiene un retraso de $\approx$\,5--6\,min}: es adecuado para
        rampas, pero en picos cortos la capacidad llega tarde. Para la campaña se recomienda un
        perfil programado o autoscale predictivo.
  \item \textbf{Lecciones operativas.} En redes domésticas aparecen artefactos de medición
        (retransmisiones SYN de 1,2\,s) que deben separarse de la saturación real. Las cuotas y
        las restricciones de SKU por zona condicionan el diseño desde el inicio. Los
        \emph{security defaults} de Entra ID bloquean el flujo \emph{device code} de la CLI.
\end{enumerate}

Todos los recursos se eliminaron al terminar con \texttt{terraform destroy}, verificado en el
portal (ver \texttt{README.md}).
